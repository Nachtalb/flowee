# Configuration

An instance is one deployment of the Worker. Its configuration is **instance options** (Worker vars), the
**workspace documents** and the **secrets** those documents name.

## Instance

| Var | Values | Default | Meaning |
|---|---|---|---|
| `FLOWEE_MODE` | `standalone`, `managed` | `standalone` (`bun run deploy`: `managed` when the document has `instance`) | Standalone: exactly the workspaces configured at deploy, one bot, nothing creates or changes a workspace at run time; management commands and updates are ignored, `/admin/*` answers `501 unsupported` and no managed-bot method is ever called. Managed: workspaces are made in the chat (docs/managed.md) or imported, kept in the Instance Durable Object; each has the instance's bot or its own managed bot. Any other value: `501 unsupported` to every request. |
| `FLOWEE_CONFIG` | JSON | `flowee.config.json` | The instance document below (or a single workspace document). As a var or a secret it wins over the committed `flowee.config.json` next to `wrangler.toml`. `bun run deploy` uploads `flowee.config.local.json` (git-ignored: a deployment's chat ids and URLs stay out of the repository) as this secret with every version; delete the secret to fall back to the committed file. In the managed mode its workspaces are preconfigured: imported at start (owner: the instance owner) and kept up to date when the document changes. |
| `FLOWEE_KEY` | secret | | Managed mode, required: the key secrets entered in the chat are sealed with (AES-GCM, key = SHA-256 of this value). Changing it makes every stored secret unreadable. |
| `FLOWEE_ADMIN_TOKEN` | secret | | Managed mode: the bearer token of the configuration API (`/admin/*`, docs/api.md); without it that API answers 401. |

The instance document is `{"flowee": 1, "workspaces": [<workspace>, …], "instance": {…}}`
(`schema/instance.schema.json`); `instance` is required in the managed mode:

| Field | Type | Default | Meaning |
|---|---|---|---|
| `instance.bot.token`, `instance.bot.webhookSecret` | secret names | required | The instance bot (Telegram: `@FloweeAgent`) with bot management enabled. |
| `instance.bot.username` | string | | Its username, shown in the wizard. |
| `instance.publicUrl` | `https://…` | required | The Worker's URL; webhooks: `<url>/telegram` (instance bot), `<url>/telegram/w/<workspace>` (own bots). |
| `instance.transport` | `webhook`, `polling` | `webhook` | How the instance bot's and the own bots' updates arrive; `polling` only self-hosted (docs/self-hosting.md), the Worker refuses it. |
| `instance.owner` | chat user id | required | The instance owner; owns the preconfigured workspaces. |
| `instance.creators` | chat user ids | `[owner]` | Who may create workspaces (the wizard and imports). Everyone else gets one sentence saying so. |
| `instance.limits.workspacesPerUser` | integer ≥ 1 | `5` | Workspaces one user may own. |
| `instance.profile` | `{name, description, shortDescription, photo}` | Flowee's own texts, the bundled photo | The instance bot's profile (docs/telegram.md). |
| `instance.trackerApi` | URL | `https://api.github.com` | The tracker API of workspaces made in the wizard. |

Workspace ids must be unique, no two workspaces may bind the same chat and topic, and a repository belongs to one
workspace only. In standalone mode every workspace with a chat must name the
same `chat.token` and `chat.webhookSecret` (one bot).

## Secrets

Documents never hold a secret, only its **name** (`^[A-Z][A-Z0-9_]*$`); the value is a Worker secret
(`wrangler secret put NAME`). An exported document therefore contains no secret, an imported one validates
without any, and `missingSecrets(doc, secrets)` lists the names the instance still lacks.

| Field naming a secret | The secret's value |
|---|---|
| `tracker.token` | the tracker token (GitHub: a fine-grained token with Issues read/write and Contents read on the repository; a classic token with `repo` + `project` when `tracker.project` is set. GitLab: a project or personal access token with `api` scope and at least the Planner role, Developer for the code features: docs/gitlab.md) |
| `roles[].secret` | the SHA-256 hex of the instance's API secret (`printf %s "$SECRET" \| sha256sum`), never the secret |
| `chat.token` | the bot token |
| `chat.webhookSecret` | a random string; Telegram sends it back with every update |
| `files.token` | the upload endpoint's token |

## The workspace document

One JSON document is a workspace's whole configuration: flow, tracker, roles, owners, chat, texts, schedule.
`schema/workspace.schema.json` is its JSON Schema (generated by `bun run schema` from `src/config/schema.ts`; a
test keeps both and the TypeScript types in step). The validator reports every problem as one sentence starting
with its JSON path, e.g. `$.tracker.repos: must have at least 1 item(s).` Check a document before submitting it
with the same validator the Worker runs: `bun run validate <file>…` (a workspace or an instance document; exit 0
valid, 1 a problem, 2 unreadable).

### Several repositories

A workspace has one flow over one or several repositories. With one, a ticket is its issue number, exactly as
before: `12` in API bodies, `#12` in texts, commits end with ` (#12)`. With several, a ticket is `alias#n`
everywhere: API bodies and query strings (`{"n": "app#12"}`, `show?n=app%2312`; a bare number is refused),
responses (`"n": "app#12"`, `queue: ["app#1", "lib#1"]`), cards, lists and error texts. A commit names its
ticket with ` (#12)` in the ticket's own repository or with ` (app#12)`; only commits of the ticket's repository
(on its branch) count. `Depends on: #3, lib#4` resolves a bare `#3` in the ticket's own repository. `file`
takes an optional `repo` (an alias; default the first repository).

Queues across repositories: within each state the lower issue number goes first, and on equal numbers the
repository listed first (the board's hand-over order stays oldest hand-over first). Storage keys are the
ticket's global id: its repository's slot × 10⁹ + its number. The first repository a workspace had holds slot
0, so a one-repository workspace stores plain numbers as it always did; slots are kept per repository
(`owner/name`) in the workspace's storage, so renaming an alias or reordering the list never moves a ticket.
A repository removed and added again gets its old slot back.

Repositories may live on different trackers (`tracker.repos[].type`, `tracker.repos[].api`): each ticket's issue,
comments, commits, pull or merge request, checks, tags and releases go through its own repository's tracker, and
every feature must be one each of them can do. The same path on GitHub and on GitLab is two repositories; slots of
a non-GitHub repository are kept by `<type>:<host>/<path>`.

### Features

Each feature is off unless the document gives it: `true` switches it on with the defaults, an object with options,
`false` or absence leaves it off. Branching is `pullRequests` (off: Single branch, on: Feature branches); Versioning
is `releases`, available with either; the rest are independent options (docs/flow-features.md). A feature an inline
flow has no states for, or that its tracker cannot do, is refused. docs/flows.md ("Features") says how a flow tags them;
docs/adapters.md lists the token permission each one needs; docs/flow-features.md says what each one adds.

| Field | Type | Default | Meaning |
|---|---|---|---|
| `features.pullRequests` | `true` or object | off | A branch and a pull request per ticket. The developer pushes the branch and calls `pr` (the Worker opens or updates the pull request); `handoff` needs it open with its checks green (or merged, see `merger`). |
| `features.pullRequests.branch` | string with `{n}` | `flowee/{n}` | The ticket's branch name (the client creates it). |
| `features.pullRequests.checks` | array of names | `[]` | Checks that must be green on the pull request's head; empty: every check run and status, and at least one. |
| `features.pullRequests.method` | `merge`, `squash`, `rebase` | `merge` | How the pull request is merged; the merge commit's subject ends with the ticket suffix (` (#n)`). |
| `features.pullRequests.merger` | `flow`, `developer` | `flow` | `flow`: the tester tests the pull request's head and `pass` merges it. `developer`: the developer merges with `merge` (checks green) before `handoff`, and the tester tests the main branch. |
| `features.pullRequests.deleteBranch` | boolean | `true` | Delete the branch after the merge. |
| `features.releases` | `true` or object | off | Releases: which one contains a ticket, test cards held until then, the version line, the `tested` tag. |
| `features.releases.source` | `release`, `tag` | `release` | `release`: the latest published release (its notes' `build from <sha>` names the built commit, else its tag's commit). `tag`: the commit `tag` points at (a moving tag). |
| `features.releases.tag` | string | | The tag marking the published build (`source: "tag"`, required there). |
| `features.releases.testedTag` | string | | A tag the cron moves forward over the main branch as far as no commit belongs to a ticket still in an untested state (`meta.untested`); CI can release from it. |
| `features.releases.checks` | array of names | `[]` | `testedTag` lands only on a commit with these checks green. |
| `features.releases.skip` | array of commit types | `["docs", "chore", "test"]` | `testedTag` never lands on a commit of these types. |
| `features.releases.hold` | boolean | `true` | A `Kind: test` card for a ticket whose commits the release lacks waits in `awaiting release`; the cron hands it to the owner when a release has them. |
| `features.releases.versionLine` | boolean | `true` | Test cards say `📦 In <version> or later`: the first of the last 10 published releases that has every commit of the ticket (the minimum version to install); no line while no published build has them all, or for a ticket without commits. |
| `features.samples` | `true` or object | off | The `sampler` role and the states `needs samples`, `in procurement`, `samples unobtainable`; `Kind: sample` cards. |
| `features.samples.root` | string | `""` | Sample paths must start with this (e.g. `Samples/`). |
| `features.samples.notNeededLabel` | string | `not file related` | A ticket with this label needs no sample to become `ready`. |
| `features.uiReview` | object | off | A `pass` whose commits change the UI goes to `board review` with an owner card instead of closing. |
| `features.uiReview.paths` | array of globs | `[]` | A change to a file under one of them is a UI change (`**/ui/**`, `**/src/main/res/**`). |
| `features.uiReview.addedFiles` | array of globs | `[]` | A file added under one of them is a UI change (a new view). |
| `features.uiReview.addedLines` | array of regular expressions | `[]` | An added line matching one is a UI change (`@Composable`). |
| `features.uiReview.ignore` | array of globs | `[]` | Files never counted (`formats/**`, tests). |
| `features.dependencyTickets` | `true` or object | off | The cron files one ticket per open pull request of these authors (`deps: <title> (PR #p)`, body `Pull request: #p`); its hand-off needs that pull request merged. |
| `features.dependencyTickets.authors` | array | `["dependabot[bot]"]` | Pull request authors. |
| `features.dependencyTickets.labels` | array | `[]` | Labels the ticket gets (e.g. `not file related`). |
| `features.untrustedReports` | `true` or object | off | A ticket labelled as untrusted user text goes only to `role` (in any state) until `triage` or `checked` removes the label. |
| `features.untrustedReports.label` | string | `feedback` | The label an outside service puts on untrusted text. |
| `features.untrustedReports.role` | string | `board` | The role that reviews it. |

### Invalid combinations (one sentence each)

- A `roles[].role` that is no role of the flow; an `instance` used twice.
- Two repositories with the same alias, the same repository twice on one tracker, or a name that gives no usable alias.
- A repository path that is not of its tracker's form (GitHub: `owner/name`); a repository whose `type` differs from
  `tracker.type` without its own `token`; `tracker.project` (a GitHub board) without any GitHub repository.
- No instance with the flow's owner role (`trunk`: `owner`): the owner could not answer through the API.
- `chat` without any `owners[].chat`.
- `files` without `chat`; `profile` without `chat.publicUrl` (unless `chat.transport` is `polling`).
- `schedule.digestFrom` not before `schedule.digestTo`; a `schedule.timezone` that is no IANA zone.
- An inline `flow` that does not load (every problem of docs/flows.md's checks).
- A feature the flow has no states for, or that the tracker cannot do (`$.features.samples: the inline flow has no
  feature 'samples'.`); `releases.source: "tag"` without `releases.tag`; `releases.testedTag` equal to `releases.tag`;
  `uiReview` without any of `paths`, `addedFiles`, `addedLines`, or with an `addedLines` entry that is no regular
  expression; `untrustedReports.role` that is no role of the flow; an instance of a role whose feature is off.
- In an instance document: a workspace id twice; two workspaces bound to the same chat and topic; one repository
  in two workspaces (their claims and tickets would clash); (standalone) two different bots.

## Secrets in the managed mode

Workspaces made in the chat name their own secret slots, `W_<ID>_TRACKER`, `W_<ID>_BOT`, `W_<ID>_HOOK` and
`W_<ID>_<INSTANCE>`; the values are sealed in the Instance object's storage (AES-GCM under `FLOWEE_KEY`), never
logged, echoed or exported. A slot named by a document that is neither sealed there nor a Worker secret is
missing: the wizard asks for it (the tracker token as a message it deletes at once), generates it (agents'
secrets: shown once, only the SHA-256 kept) or the API takes it (`PUT /admin/workspaces/<id>/secrets`). A
document imported in the chat always gets the workspace's own slots, so it can never reach another workspace's
token; the configuration API (the operator's) keeps the names it is given.

## Export and import

`WorkspaceRegistry.export(id)` returns the document as imported; `exportAll()` the instance document;
`import(doc)` creates or replaces one workspace after validating it (and the instance with it); `importAll(doc)`
replaces them all. Nothing changes when a document is invalid. In standalone mode the registry is built from
`FLOWEE_CONFIG` at start; to change a workspace, edit the document and deploy.

# Flowee: install and set up

Set up a Flowee instance (a Cloudflare Worker) and a project that uses it. Two modes; pick with the user first:

| Mode | When | Who configures |
|---|---|---|
| **standalone** (the document has no `instance`) | one team, fixed workspaces | you: the workspace document is deployed with the Worker |
| **managed** (the document has an `instance` section) | several people or projects set up workspaces themselves | you deploy once; each user runs the setup wizard in the chat |

The deployment's document is `flowee.config.local.json` (git-ignored: owner ids, chat ids and URLs never reach the
public repository). `bun run deploy` validates it, sets `FLOWEE_MODE` from it, uploads it as the `FLOWEE_CONFIG`
secret with the version and calls `<publicUrl>/setup`. Never edit `wrangler.toml` or `flowee.config.json` for one
deployment.

The workspace document itself: skill [flowee-configure](../flowee-configure/SKILL.md). Agents' daily use: skill
[flowee-use](../flowee-use/SKILL.md). The exact verification commands and what they print:
[references/verify.md](references/verify.md). Project repository, role clones, the project key, the agents and scheduled runs:
[references/project-setup.md](references/project-setup.md). These files read the same from a clone of the repository
and from an instance (`<url>/skills/flowee-install/SKILL.md`): every relative link resolves in both.

## Starting from an instance URL

When you were given the URL of a running Flowee instance instead of this repository ("use <url> to set Flowee up"),
you deploy nothing: the "Standalone", "Managed" and "Self-hosted" sections below are for whoever operates an instance.

1. `curl -fsSL <url>/` (the same as `<url>/llms.txt`): the instance's own facts (mode, version, bot, trackers, who may
   create workspaces) and the procedure with the questions to ask the user. It is generated by that instance, so it
   matches its version; where it and this skill differ, it wins.
2. `curl -fsSL <url>/bundle.tar.gz | tar -xz`: these skills, the docs, the agent role templates, the client, the
   schema and the flow, as that instance serves them (`flowee/`). Copy the three directories under `flowee/skills/`
   into your skills directory, or read them in place.
3. Ask the user the root document's questions in one message; write the workspace document
   ([flowee-configure](../flowee-configure/SKILL.md)); check it with `POST <url>/validate` (no token; nothing is
   stored) until it answers `{"ok": true, ...}`; show it to the user, who submits it the way the root document says.
4. The project side ([references/project-setup.md](references/project-setup.md)) with the client from
   `<url>/client/flowee.py`; verify with `python3 scripts/flowee.py version` and the rows "the project key", "the
   agents" and "the queue" of [references/verify.md](references/verify.md).

## Rules

- **Never print a secret.** Pipe values straight into `wrangler secret put NAME` (from a password manager, a file,
  or `openssl rand -hex 32`); never echo them, never pass them as arguments, never write them into the repository.
- **Ask before deploying to the user's account**; check `bunx wrangler whoami` first.
- **Validate before deploy**: `bun run validate flowee.config.local.json` must print `ok` (`bun run deploy` checks it
  again and refuses an invalid one).
- **Verify each step** with the commands in `references/verify.md`; report what they printed, not what should
  happen.
- **Tests never touch a real remote.** `bun run test` and `test/e2e/wire.py` use fakes and local stand-ins of GitHub
  and GitLab.

## Standalone

1. `git clone https://github.com/Nachtalb/flowee && cd flowee && bun install`; `bun run typecheck && bun run test`.
2. Write the workspace document (skill `flowee-configure`) as `flowee.config.local.json`:
   `{"flowee": 1, "workspaces": [<doc>]}`. `bun run validate flowee.config.local.json`.
3. The inbox: ask "Telegram, terminal, or both?". Terminal only: skip the bot; each person runs
   `flowee-tui --new-key` (from `bun run compile:tui`, docs/tui.md) and hands you the digest for `tui.people`; they
   sign in with `flowee-tui --url <url>`. Telegram (alone or with the terminal): create the bot with BotFather; note its username for `chat.username`. The owner's chat id: the user
   sends the bot a message and reads `getUpdates`, or uses a known id. Before using a token, `getMe` must name the
   expected bot, and `getWebhookInfo` must show no webhook (else the bot is in use elsewhere: stop and ask).
4. Tracker token. GitHub: fine-grained, limited to the workspace's repositories, with the permissions of
   `references/project-setup.md` ("Token permissions"). GitLab (`"type": "gitlab"`): a project or personal access
   token with the `api` scope and the role per feature in the same file ("GitLab"); self-managed: `tracker.api` (or
   `tracker.repos[].api`) is `https://<host>/api/v4`. A `tracker.project` board needs a classic `repo` + `project` token
   instead (a fine-grained token cannot write a user-owned project): put that trade-off to the user.
5. Secrets: every name the document references, each value on stdin (the first `secret put` creates the Worker;
   wrangler answers its "create a new Worker?" question with yes when stdin is not a terminal).
   - tracker and bot tokens: `wrangler secret put <NAME>` with the value on stdin;
   - `chat.webhookSecret`: a random string (`openssl rand -hex 32 | bunx wrangler secret put TG_WEBHOOK_SECRET`);
   - the project key (`agents.key`): generate it, give it to the machines the agents run on (mode 600, the
     `key_file`), and store only its SHA-256:
     `printf %s "$K" | sha256sum | cut -d' ' -f1 | bunx wrangler secret put ACME_KEY`. The agents then create
     themselves with it (`flowee.py roles`, `flowee.py agents add <role> <name>`; references/project-setup.md). A new
     key: the same command with a new value and `bun run deploy`.
6. `bun run deploy`: it prints `GET <url>/setup: 200 {...}` with each profile step `set` or `current` and exits
   non-zero when the deploy or `/setup` failed. `chat.publicUrl` must be the Worker's URL
   (`https://<worker>.<subdomain>.workers.dev`; wrangler prints it). Webhooks (`sync.webhooks: auto`) need the Worker
   secret `FLOWEE_KEY` (`openssl rand -hex 32 | bunx wrangler secret put FLOWEE_KEY`) and a GitHub token with
   **Webhooks: read and write** (GitLab: Maintainer + `api`); the cron registers them within a minute of `/setup`.
   Check that the ping arrived (`references/verify.md`, "webhooks registered"); without them the workspace polls.
7. Verify (`references/verify.md`), then set up the project repository and the agents (`references/project-setup.md`).

## Managed

1. As standalone step 1.
2. The instance document (`flowee-configure`, example 6) as `flowee.config.local.json`: `instance.bot` (secret names
   of the token and webhook secret, `username`), `publicUrl`, `owner` (the user's Telegram id), `creators`, limits;
   `"workspaces": []`. The workers.dev subdomain: wrangler prints the URL on the first deploy; set `publicUrl` before
   it (`GET /accounts/<id>/workers/subdomain`) or deploy again after correcting it.
3. Secrets, each on stdin, never printed or on a command line: the instance bot's token and webhook secret (random),
   `FLOWEE_KEY` (random; seals every secret entered in the chat), `FLOWEE_ADMIN_TOKEN` (random; the configuration
   API). Keep `FLOWEE_KEY` and the admin token where the operator finds them again (a password manager, or files of
   mode 600 in a 700 directory): a lost `FLOWEE_KEY` makes every stored secret unreadable. `wrangler secret list`
   then names the four (plus `FLOWEE_CONFIG` after the deploy).
4. `bun run deploy`. The instance entry of the printed `/setup` result has `name`, `description`,
   `short_description`, `commands`, `settings`, `photo`, `webhook`. `settings` also turns on bot management
   (`can_manage_bots`), so BotFather needs no step. Read the result back with `getMe`, `getMyCommands` (scope
   `all_private_chats`) and `getWebhookInfo` (`references/verify.md`).
5. Check the configuration API (`references/verify.md`, "Managed"): the workspace list empty, a wrong token 401.
6. Hand over to the user: in a private chat with the bot, `/setup` (or send a document an agent wrote). The wizard
   is one message edited step by step: the repository (its link as pasted), the bot, the way of working, where the
   tickets appear and the GitHub token (the message is deleted at once); then it sends the project key once as a file
   with a ready `.flowee.toml` and the three commands that create the agents. That part is the user's; you do not see
   the key.
   Do not message the user's chat yourself to test it.
7. Automation instead of the chat: `PUT /admin/workspaces/<id>`, `PUT /admin/workspaces/<id>/secrets` and
   `POST /admin/workspaces/<id>/key` (a new project key, answered once) with
   `Authorization: Bearer <FLOWEE_ADMIN_TOKEN>` (`references/verify.md`).

## Self-hosted (no Cloudflare)

The same documents, served by one process the operator runs (docs/self-hosting.md). Use it when the user has no
Cloudflare account or wants the data on their own machine.

1. The workspace (or instance) document as in "Standalone" (or "Managed") step 2; validate it the same way. Without a
   public URL leave `chat.publicUrl` out: `chat.transport` then defaults to `polling` (the bot's updates by
   getUpdates, no address needed) and the trackers are polled every `sync.pollMinutes`. `chat.webhookSecret` still
   names a secret, which polling never reads. Telegram as step 3; `getWebhookInfo` must show no webhook, and no
   other process may poll the bot (Flowee stops with one sentence on Telegram's 409).
2. Run it: the published image `ghcr.io/nachtalb/flowee:latest` (or `docker build -t flowee .` in a clone), `compose.yaml` as the
   template, or the executable (`bun run compile -- --target bun-linux-x64 --outfile flowee`). Configuration by
   environment: `FLOWEE_CONFIG_FILE` (the document), `FLOWEE_DATA` (one directory, one volume), every secret the
   document names as a variable or as `<NAME>_FILE` (Docker secrets). The project key (and agents' secrets): the SHA-256 hex, as on the Worker.
3. `FLOWEE_KEY`: leave it out and the first start generates `<data>/flowee.key` and says so in the log; tell the
   operator to back that file up with the data directory (backup = copy the directory while stopped).
4. Behind a reverse proxy (https): `FLOWEE_PUBLIC_URL=https://…` (and `FLOWEE_TRUST_PROXY=1`); Telegram and tracker
   webhooks then register at start as on the Worker. The managed mode needs `instance.publicUrl` either way; set
   `instance.transport: polling` to poll its bots.
5. Verify: `flowee health` (or `GET /health`) is 200, the log says `polling for updates` per bot (or `listening` and
   the setup results), `GET /` names "a self-hosted Flowee process" and the transport; then `references/verify.md`
   as for standalone, with the instance's own URL (e.g. `http://127.0.0.1:8787`).

## Pitfalls found while building it

- A stray `~/.wrangler/` (left by test runs) takes precedence over `~/.config/.wrangler/` and hides the wrangler
  login: wrangler then asks for `CLOUDFLARE_API_TOKEN`. `ls -d ~/.wrangler` before deploying; remove it.
- Python's default `Python-urllib` User-Agent gets `403 error code: 1010` from Cloudflare even on `*.workers.dev`.
  `flowee.py` sends `flowee/<version>`; any other client must send its own User-Agent too.
- Changing `FLOWEE_KEY` makes every secret stored through the chat unreadable; every workspace then needs its
  tokens again. Keep the key in a password manager.
- A fine-grained GitHub token cannot write a user-owned Project (v2). Without `tracker.project` the labels are the
  state and the narrow token suffices.
- `agents.key` (and `roles[].secret`) holds the SHA-256 hex of the key, never the key: a raw key there means no agent
  can authenticate (`401 unauthorized`).
- The project key acts as any agent of the workspace: role separation is by convention. Where it must be enforced, the
  document says `agents.secrets: "per-agent"` (docs/api.md, "One key or a secret per agent").
- One repository belongs to one workspace per instance; a second workspace naming it is refused.
- In a group, the bot runs in privacy mode: the owner answers by replying to a card.
- A changed document takes effect only with a new `bun run deploy` (standalone: the workspaces; managed: the instance
  section). A plain `wrangler deploy` uses the `FLOWEE_MODE` of `wrangler.toml` (standalone) and skips `/setup`.
- `setMySettings` as the live API answers it ([docs/telegram.md](../../docs/telegram.md)): `has_topic_sidebar` only sticks while
  `has_topics_enabled` is on; `callback_query_mode` is not readable back.
